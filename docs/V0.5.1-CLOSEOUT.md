## 1. Executive decision

The decision recorded here closes, rather than extends, the v0.5 expansion
cycle for v0.5.1 once its lifecycle reaches `ACCEPTED`.

When this record is `ACCEPTED`, the project retains:

- the released profile, schemas, templates, validator, and reusable workflow;
- the thin, read-only, source-checkout `aap check` facade;
- the characterization and decision records;
- the released diagnostic-candidate data, verifier, and tests, frozen as a
  central candidate-integrity CI surface rather than an adopter or runtime
  contract; and
- the maintainer-observed value of using AAP to reconstruct a system, expose
  contradictions, and bring decisions to its human owner.

In that state, the v0.5 architecture and diagnostic-expansion track is
**scope-frozen and evidence-gated**. This decision does not archive AAP or
declare the whole repository maintenance-only. It stops open-ended expansion
of this track until real adopter evidence authorizes a bounded next step.

The project does not currently authorize:

- a canonical Snapshot engine;
- acceptance or runtime use of the diagnostic-catalog candidate;
- further semantic-guard expansion whose only consumer is an unaccepted,
  review-only candidate;
- acceptance verification written before a real acceptance record and runtime
  consumer exist;
- a stable public diagnostic protocol, package, or broader CLI command suite;
  or
- claims that AAP reduces production regressions, issue-reopen rates, or
  diagnosis time.

Those outcomes are unproven. They are not release work until the evidence and
reauthorization conditions below are met.

## 2. Why this closeout exists

The maintainer's practical experience is mixed but meaningful:

- applying AAP appears to improve understanding of a large, agent-built
  codebase;
- comparing intended conditions with implementation has exposed real
  contradictions and prompted useful remediation;
- the volume of code makes unaided whole-repository review impractical; and
- repeated open-ended review has not shown a credible convergence pattern.

The repository also records two maintainer-affiliated pilot adoptions that
produced concrete schema, pinning, workflow, and prose-authority corrections.
They are useful discovery evidence, not independent evidence that AAP lowers
regression rates, issue rates, or diagnosis time.

The recurring loop was:

```text
open-ended whole-repository review
  -> candidate finding
  -> local fix, guard, or regression test
  -> larger review and maintenance surface
  -> another open-ended review
```

This does not mean that each finding or fix was wrong. It means the process had
no externally bounded stopping objective. A review pass is a
candidate-finding mechanism, not an exhaustive proof procedure. A new finding
is not automatically a release blocker, and a pass with no finding proves only
the bounded coverage of that pass.

AAP is finished for this release when the important promises,
contradictions, evidence gaps, and remaining risks have explicit
dispositions. “A fresh review found nothing else” is not a completion
condition.

This record keeps unlike evidence separate:

| Class | Meaning |
|---|---|
| `CODE-VERIFIED` | Directly established by repository content at the named revision |
| `RECORD-VERIFIED` | The named bytes, change, or recorded act exist in repository history; this alone does not authenticate an external human act |
| `MAINTAINER-OBSERVED` | Reported from actual use but not measured experimentally |
| `REVIEW-HYPOTHESIS` | A useful external explanation, not established causality |
| `UNKNOWN` | The present evidence cannot support the claim |

Improved understanding and surfaced contradictions are
`MAINTAINER-OBSERVED`. The runtime boundaries and decision states below are
`CODE-VERIFIED` or `RECORD-VERIFIED`. When a statement depends on human
authority, the linked durable human approval act must be checked separately;
committed prose alone cannot supply it. Adopter outcome improvement remains
`UNKNOWN`.

## 3. What the external discussion establishes — and does not

The external discussion separated several possible causes of repeated
regressions: long-context degradation, accumulated local patches, missing
behavioral baselines, increased user exposure, and architectural coupling.
That separation is useful, but it is discussion input rather than an
independent technical review of this repository.

The defensible synthesis is:

1. Long-context degradation is real. The
   [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) study shows
   position-sensitive degradation in multi-document question answering and
   key-value retrieval. It does not establish the cause of regressions in
   these software projects.
2. Context loss is neither a necessary nor a sufficient cause of local
   patching. It can still amplify it by making earlier constraints less
   salient.
3. The effective objective is shaped by the prompt, visible tests, termination
   rule, tools, search budget, and review process. If success means only
   removing the latest symptom, global consistency has no reliable gate even
   in a short session.
4. A 2026 preprint on
   [regression accumulation in multi-turn programming](https://arxiv.org/abs/2607.01855)
   reports cross-turn conflict as its dominant reviewed failure class and finds
   that re-running prior tests as a verification gate consistently improves
   the evaluated models. It supports verification gates, but its synthetic
   eight-turn benchmark does not prove the causal mix in a real repository.
5. Characterization tests establish a previous behavior baseline; they do not
   decide whether that behavior was intended. Human intent review remains
   necessary.

The immediate control is therefore not a universal causal claim. It is a
bounded objective, executable verification of selected invariants, explicit
residuals, and a stopping rule.

## 6. What AAP is — and is not

AAP's present product is a repository assurance and governance layer. It is
useful for:

- reconstructing purpose, boundaries, promises, and uncertainty;
- separating current behavior from human-approved intent;
- identifying contradictions among policy artifacts and code evidence;
- keeping stable links among invariants, controls, evidence, and residuals;
- preventing a class of structural, pinning, path-trust, review-stage, and
  policy-weakening mistakes; and
- ensuring that decisions requiring human authority remain visible.

It is not:

- an exhaustive code auditor;
- a product-test runner or a replacement for project CI;
- a proof that referenced evidence is true;
- an automatic classifier that discovers every applicable profile;
- a guarantee that an adopting project has no bugs or regressions; or
- a reason to turn every speculative finding into a permanent control.

This boundary explains the maintainer's positive experience without
overstating it: the maintainer reports improved understanding and surfaced
contradictions, while evidence that AAP lowers issue rates remains absent.

## 7. Minimum Effective Adoption

Once `ACCEPTED`, this closeout designates
[ADOPTION.md §1.1](ADOPTION.md#11-minimum-effective-adoption-agent-led-with-two-human-decision-touchpoints)
as the single detailed recommended operating procedure for a new focused
adoption or a voluntary re-baseline. Existing adopters need not migrate
artifacts, repeat their initial assessment or baseline decision, or change
their declared stage merely because they upgrade the pin; the ordinary
pin-upgrade review still applies. This closeout records the policy choice; it
does not duplicate the procedure.

- `DRAFT` is a mechanically checked scaffold, not an effectiveness claim.
- For an active repository, `HUMAN_REVIEWED` is the normal first target when
  its actual stage conditions are met. Roughly five to ten ranked invariants is
  a starting target, never a cap: every identified critical invariant and
  every applicable profile obligation remains in scope.
- `CONFORMANT` is optional and should be declared only when the project needs
  and can support the full bounded claim.
- An exclusive `archived` adoption follows its own narrow path: establish
  reference-only eligibility, install the pin and root guides, reconstruct and
  owner-confirm the four §6.6 historical facts, and do not fabricate active
  registers or tests.

“Effective,” the target size, two assessment passes, and two human touchpoints
are design hypotheses for the bounded pilot in §12, not measured outcomes or
new conformance rules.

Adoption starts with the exact trigger rules in
[PROFILE.md §5](../PROFILE.md) and the challenge procedure in
[ADOPTION.md §4.0](ADOPTION.md). The agent proposes and attacks the smallest
set covering every fired trigger; the human owner confirms it. The validator
enforces the declared set but does not prove that no applicable profile was
omitted.

## 8. Human-attention budget

AAP's human interaction contract lives in
[ADOPTION.md §1.1](ADOPTION.md#11-minimum-effective-adoption-agent-led-with-two-human-decision-touchpoints);
the plain-language mirror is [REVIEW-GUIDE.md](REVIEW-GUIDE.md#fast-path).
The governing decisions are:

- the agent answers everything that code, tests, history, runtime evidence, or
  mechanical validation can answer;
- the normal first adoption has two planned human decision touchpoints: scope
  once (already satisfied when the kick-off instruction supplies it), then one
  consolidated baseline decision cycle;
- an active packet contains the critical intent, claim, wording, and residual
  decisions; an archived packet instead contains eligibility and the four
  historical facts;
- one page is a presentation target, with a bounded annex whenever completeness
  requires it; and
- general baseline approval accepts no residual. The human can accept several
  in the same reply, but must explicitly name each ID, rationale, and review
  trigger; a critical acceptance must come from the owner.

Safety-sensitive disclosure or genuinely missing scope or authority can
require an extra immediate question. All other human-only decisions are
batched. Renewed operation, functional maintenance, or feature development in
an archived repository first requires owner-approved active-profile
reclassification.

## 9. Convergence and stop rules

Candidate-finding triage and residual lifecycle use different vocabularies:

| Candidate-finding disposition | Meaning |
|---|---|
| `REMEDIATE_SEPARATELY` | Open a named issue or scoped change; the read-only assessment does not contain the functional fix |
| `RECORD_AS_OPEN_RESIDUAL` | Record the remaining limitation as `OPEN`, with an owner and review trigger |
| `DEFER` | Postpone work until named evidence or demand exists, preserving any remaining uncertainty |
| `REJECT` | The candidate finding is unsupported, duplicate, out of scope, or not worth permanent control |

For an existing residual:

| Human disposition | Register result |
|---|---|
| `KEEP_OPEN` | stays `OPEN`, with ownership and a review trigger |
| `ACCEPT` | becomes `ACCEPTED` only after the named human act, date, rationale, and review trigger; critical acceptance is owner-only |
| `RESOLVE` | becomes `RESOLVED` only with resolution grounds and a remediation reference |

Requesting remediation does not close a residual. It remains `OPEN` until the
separate change supplies the grounds for `RESOLVED`. `REJECT` records a review
rationale without manufacturing a residual when no uncertainty remains.

The active assessment stops after the predeclared reconstruction and challenge
passes when all required owner decisions about critical invariants, material
behaviors, critical claims, and applicable public wording in that scope are
dispositioned; every candidate finding surfaced within those passes that would
have residual `impact: high` or `impact: critical` has one of the four
dispositions above; all mandatory references are present; no release blocker
is untriaged; and the applicable `HUMAN_REVIEWED` conditions hold. The archived
assessment instead stops on its exclusive eligibility, four owner-confirmed
facts, complete pin and artifacts, recorded material uncertainty, and
applicable stage conditions.

Success stops discovery immediately. If the predeclared budget expires first,
stop discovery and hand off the bounded result; retain `DRAFT` whenever a
stage-mandatory obligation, undispositioned critical contradiction, or
required owner decision is still unresolved. Neither path waits for a
zero-finding pass.

In an active repository, a new permanent invariant, control, or regression
test should protect a reproduced defect, an explicit user or operator promise,
or a named critical safety, security, integrity, or governance case. An
isolated speculative finding is recorded or rejected; it is not automatically
promoted into permanent machinery. The exact operational completion rules
remain canonical in
[ADOPTION.md §1.1](ADOPTION.md#completion-and-expansion-rules).

## 10. v0.5.1 release scope

`v0.5.1` is intended to be a documentation and maintenance closeout.

Included:

- this closeout record and synchronized README/CHANGELOG direction;
- the agent-led Minimum Effective Adoption guidance;
- preservation of released `v0.5.0` behavior, including the existing
  candidate-integrity verifier and tests in central test discovery, without
  extending them;
- correction of the released candidate documentation's verifier-test count
  from 23 to 24; and
- a correction needed to prevent a reproduced false-green, false-red, security
  defect, compatibility break, or materially misleading adoption instruction.

Excluded unless separately reauthorized:

- post-`v0.5.0` expansion that only hardens the unaccepted diagnostic
  candidate;
- acceptance or runtime consumption of that candidate;
- a canonical engine or stable public diagnostic protocol;
- a package or `init`, `review`, or `migrate` command suite;
- new normative obligations, schema fields, or adopter migrations; and
- new verification machinery with no accepted record and scheduled consumer.

The release must be prepared from a clean baseline that excludes unaccepted
post-`v0.5.0` diagnostic expansion. Exclusion does not declare the experiment
worthless; it records that it has not earned release scope.

## 11. Ordinary maintenance and evidence-gated v0.5-track reopening

Ordinary documentation corrections, dependency and CI upkeep, and bounded
fixes to released profile, validator, or workflow behavior continue under
[CONTRIBUTING.md](../CONTRIBUTING.md),
[GOVERNANCE.md](../GOVERNANCE.md), [SECURITY.md](../SECURITY.md), and the
ordinary release process. They do not require a reopening decision merely
because they change this repository.

A proposal to reopen or expand the scope-frozen v0.5 architecture and
diagnostic track needs one of:

- a minimal reproduction of a released false-green or false-red;
- a bounded security or trust-boundary defect;
- a reproduced compatibility break in a supported environment;
- a materially misleading instruction that blocked a real adopter; or
- the same bounded need observed in two independent adopters.

“Another review found a possible issue” is not, by itself, a trigger to reopen
or expand that track.

Feature development within that track resumes only through a new bounded
decision that names:

1. a human owner;
2. the concrete adopter problem and affected consumer;
3. the smallest proposed scope;
4. the evidence threshold and success metric;
5. an effort or time cap;
6. a stop condition; and
7. the residual if the work does not proceed.

Feature work outside that track follows the ordinary governance and release
rules.

The canonical engine additionally remains subject to the existing G1
requirements. Any diagnostic-catalog expansion or runtime promotion
additionally requires a named runtime consumer and a record-first acceptance
decision. A new verifier follows that decision; it does not create it. The
candidate-integrity verifier retained in §10 is a frozen exception carried
forward from the released baseline, not precedent for further expansion.

## 12. Bounded adopter pilot

Before reopening or expanding the v0.5 architecture and diagnostic track, use
the released profile in one real active brownfield repository with a
pre-registered budget.

The agent should:

1. fix the repository boundary and applicable profiles;
2. target five to ten invariants from actual incidents or material promises
   after deduplication, while retaining every identified critical invariant;
3. connect each critical invariant to project-owned executable verification or
   record an explicit gap without using that gap to replace any mandatory
   enforcement or verification reference;
4. map only the two to four highest-risk components initially;
5. run the normal project tests in project CI — outside `aap check`;
6. perform one reconstruction pass and one fresh-context challenge pass; and
7. deliver the single human decision packet.

Where a comparable prior window exists, measure:

- confirmed contradictions or missing decisions found per material change;
- regressions and reopened issues per material change;
- time to reproduce and diagnose failures;
- human review minutes;
- agent time; and
- AAP-only artifact and test churn.

Where available, also record change size and type, release count, product-test
surface, user activity or traffic, and a fixed post-deployment observation
window. Without those covariates, a change in reported issues cannot separate
exposure from change risk.

Set the duration or number of material changes, maintenance-time budget,
success threshold, and stop threshold before starting. One pilot can justify
keeping, simplifying, or archiving a feature. It cannot establish universal
effectiveness.
